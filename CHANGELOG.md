# Changelog

All notable changes to Hyperceps (and, below its own entries, to the original Cordyceps) are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## Hyperceps [1.1.1] - 2026-11-25

### Changed

- **A new icon** - The component and the Package Manager show Hyperceps' own icon: two interlaced loops on an orange badge. The component's 24 px icon is drawn for that size (one dark band per loop), and the package now carries a 64 px icon instead of the component's 24 px one. The source is in `packaging/icon` (two SVG files; `render.ps1` makes the 24, 64 and 512 px PNGs).
- **The package description is plain text** - Food4Rhino shows a package's description as written, so its bold marks would appear as `**`. The description no longer uses them.
- **Skill: saving is the user's** - The skill told the agent to save a definition that had no file before building and after each block, so a stuck script wouldn't lose it. Saving is now left to the user: the skill and `gh_document`'s save help say to save only when the user asks. The save action itself is unchanged.

## Hyperceps [1.1.0] - 2026-11-14

### Added

- **The plugin carries its own skill: nothing to install** - `gh_inspect(action='skill')` returns the Hyperceps guide, the text of the `hyperceps` skill (SKILL.md without its front matter, as Claude's Skill tool gives it), and the resource `gh://skill` serves the same file. It is embedded in `Hyperceps.gha` from `skills/hyperceps/SKILL.md` at build time, so it always matches the plugin's version. An app without the installed skill (a Claude Code without the skill folder, or another app connected to Hyperceps) reads it in one call, as many as loading the skill takes. The call doesn't touch the document, so it answers while Grasshopper is busy. The installable skill stays, and is now optional. gh_inspect gains one action; host-free core in `Core/SkillText`, unit-tested (the embedded copy is the repository's file).
- **`gh_script` `solve=true`: a script's results in the same call** - On `set` and `configure`, `solve=true` solves once after the code is written and adds `results` (each output's count, branches and first 10 values, in the shape of `gh_inspect(action='outputs')`), `messages` (errors, warnings and remarks, compile errors included) and `solveMs`. A checking script then takes one call per round instead of `set` plus `outputs`; in a benchmark run that was 8 rounds. It doesn't solve inside a cluster editor or while the solver is off (`solved: false` and `notSolved` say why). Without `solve`, both actions answer exactly as before. gh_script gains one optional input, `solve`.
- **`gh_batch` `options.watch`: build a block and check it in one call** - `options={"watch": ["PAIRS", "checker.report"]}` names up to 10 outputs (an object, `obj.port`, or a ref created in the same batch); after the batch's single solve the result adds `watch`, one line per output with its item count, branch count, up to three short text, number or true/false values, and `(not solved)` when it didn't solve. The lines are the ones `gh_document(action='sweep')` gives. A watched name that doesn't resolve is an error like any other, so nothing changes. Checking a block's counts, or wiring a checker script and reading its report, no longer needs a second call (`gh_inspect(action='tree')` stays the check for branch paths). Without `watch`, the result is exactly as before. Sweep and gh_batch now read outputs through the same code (`Tools/Batch/WatchedOutputs`).
- **`gh_script(action='edit')`: change part of a script without sending all of it** - `edits='[{"old": "exact text", "new": "replacement"}]'` replaces passages of the script's current source, in order, and writes the result exactly as `set` does (rebuild, verification, `lostConnections`; `solve=true` adds results and messages), plus `edited`, `editedLines` and `sourceLength`. Each `old` must occur exactly once; if any edit fails, nothing changes and every problem is listed, with the closest line when the text wasn't found or the lines where it occurs several times. Windows and Unix line endings both match, and the script keeps its own. From a session where an agent rewrote a 40,000-70,000-character C# script in full about 25 times to change a few lines each round (about 1.2 million characters typed, most of the session's cost). The skill now says to edit rather than resend, never to read your own script back, and to keep scripts to one stage each. gh_script gains one optional input, `edits`; host-free core in `Core/ScriptEdits`, unit-tested.
- **`outline` opens a whole network, or the objects outside groups, in one call** - On a canvas without groups, `group='network 1'` (`'network'` when there is only one; numbered as the overview lists them, largest first) lists every object of that network in the group view's format: one line each, upstream first, with what feeds each input, port settings, stored values, problems and remarks. `group='ungrouped'` does the same for the objects outside any group on a canvas that has groups, with what crosses in and out. Up to 250 lines per call; any rest are named so they can be opened with `id=`. A real group with one of these names wins. The overview's hint names the new views. In a benchmark run on a definition of 164 objects in one network and no groups, an agent traced it through nine `id=` views in a row; `group='network'` lists all 164 in one call. `gh_canvas` gains no inputs: these are names `group=` accepts. Host-free core in `Core/Outline/CanvasOutline.Regions`, unit-tested.
- **`gh_document(action='save')` without a path saves to the definition's own file** - `path` is now optional: left out, the definition is saved to the file it was opened from or last saved to, so an agent saving after each block doesn't repeat a long path. A definition that was never saved still needs one, and the error says to ask the user where it should go.

### Changed

- **A connection note that fits** - Claude Code shows only the first 4,096 characters of a server's connection note. The 1.0.0 note was 7,473 and was cut in the middle of its tool list, so its status block, busy guidance and key points never reached Claude Code agents. The note is now 3,830 characters: name and version, then "GUIDE FIRST" (load the installed skill, otherwise call `gh_inspect(action='skill')`; if a loaded skill names another version, use the plugin's copy and tell the user once), the working method, naming, Lichen Thalli, a few lines each on script edits, a busy Grasshopper and clusters, and the resources. The tool list (each tool's description carries its actions) and the details already in the guide and `gh://docs/getting-started` were taken out. It no longer asks the agent to tell the user to install the skill. The note is in `Core/ServerNote`; a unit test keeps it under 3,900 characters.
- **A refused `gh_script` edit shows the lines it missed** - When an edit's `old` text isn't in the script, the error now shows, after the closest line, the lines around it as they now read (numbered, up to eight), so the edit can be corrected without reading the script again. When those lines are a C# `RunScript` parameter list, it adds that `configure` keeps that list in step with the ports, so only the body should be edited. In a benchmark run on a 918-line script, one such miss made the agent read all 47,000 characters again; with `get` and `info` (which also returns the whole source) it read the script three times in one round. The skill, `gh_script`'s help and the guides now also say to read a script once, with `get`, and to use `outline` for only its ports and wiring. `info`'s and `configure`'s results are unchanged.
- **Skill: add a port to a script without resending it** - In a benchmark run, each time a change needed a new input (a panel for a new limit), the agent sent the whole script again with the `configure` that added the input, 219 lines the second time, although the skill says to edit rather than resend. In another run, an `edit` written just after `configure` added an output missed, because `configure` had already added the port to the C# `RunScript` line. The skill now says: to add or remove a port, call `configure` with only `inputs` / `outputs` (no `code`), then `edit` the lines that use it; in C#, `configure` adds the port to `RunScript` itself, so edit only the body.
- **Skill: sweep a slider only when the request needs it** - The working loop said "if the block depends on a slider, sweep it", and in a benchmark run an agent swept the radius slider it had just added, which nobody asked for. It now says to sweep when the request is about results across a slider's values, or after changing logic an existing slider drives; a value you set, or a slider you just added, needs no sweep, since the batch's `watch` already shows the result at that value.
- **Skill: what to do about slow or stuck scripts** - From a real session where a checker script got new code before it was rewired, ran on thousands of objects instead of a handful, and held Grasshopper until Rhino was closed (losing the unsaved definition): rewire a script before sending code meant for other inputs, bound a checker's work, save an unsaved definition before building and after each block, and after a call times out check with `gh_inspect(action='connection')` instead of calls that wait for Grasshopper.
- **A busy Grasshopper answers instead of hanging** - Every call that needs Grasshopper now checks first. While Grasshopper is solving, not responding, or busy with another call, the call waits up to 15 s; if it is still busy, it stops before reaching Grasshopper and says what is solving and for how long (`Grasshopper has been solving 'X' for 3 min 20 s, so this call stopped before reaching it...`). Before, it waited until the AI app gave up after about a minute with only "The operation timed out": in a real session a runaway checker script held Grasshopper for 7 minutes and six calls in a row ended that way. `gh_batch` waits for a running solve at most 15 s (or `timeoutSeconds` if shorter) for the same reason, and changes nothing. A "solving" flag older than 10 s on a host that still answers counts as free, so a missed end-of-solve event can't refuse every call. The check is `Core/HostBusyGate`, unit-tested, at the one place calls enter Grasshopper.
- **`gh_batch`: a built-in component wins over plugin namesakes** - A type name shared by exactly one built-in Grasshopper component and only plugin components (Offset Curve in Grasshopper and Pufferfish) now uses the built-in one, with a warning naming the plugin's (`'Pufferfish/Offset Curve'`). Before, the batch was refused and the agent had to resend it with `Curve/Offset Curve`. Two built-ins (Line the component and Line the parameter), two plugins, or a type of unknown origin are still refused with the candidates listed.

### Fixed

- **A `gh_script` edit whose write fails no longer says what it edited** - When the write after an edit failed, the answer still carried `edited`, `editedLines` and `sourceLength` beside `success: false`, as if something had changed. They (and `notes`) are now added only when the write succeeded. Found by an independent review.
- **A sweep decides when to restore from more than its last value** - Whether a sweep puts the control back after its answer was decided from the last value's solve only, so fast values with a slow original value (ten values of 3 s, an original of 34 s) still restored inside the call and could outlast the AI app's limit. Now the restore happens after the answer when the slowest value or the original value took over 5 s (the original's time is read from Grasshopper's own per-component times of what the control feeds, before the sweep starts), when more than 15 s has been spent, or when a value failed (the error is the answer). Faster sweeps restore inside the call as before. Found by an independent review.
- **A refused `gh_script` edit points at the passage it meant; trailing spaces are ignored** - When an edit's first line is a common one (`{`, `else`) that occurs several times, the error now shows the occurrence whose following lines are closest to the rest of the text, not the first in the script; and a line shortened in the error says so (`… [shortened; 412 characters]`). If the exact text isn't found, spaces and tabs at the ends of lines (in the script or in the text) are now ignored, like line endings already were: the edit applies if the text then occurs exactly once, indentation still has to match, an exact match is always tried first, and the answer's new `notes` names the lines (`edits[2] matched ignoring trailing spaces on lines 41-42`). Trailing spaces inside a multi-line text literal on the replaced lines would be dropped; the note names the lines. Found by an independent review; the owner chose to accept such edits rather than refuse them.
- **No false "modal dialog" at the end of a long solve; a sweep waits for a running solve** - The status that says "a modal dialog is almost certainly open" means the UI thread hasn't answered for 5 s while nothing is solving. That is also true for a moment at the end of every solve longer than 5 s, between Grasshopper clearing "solving" and the next heartbeat landing (confirmed live: under 0.1 s, caught twice in three 8 s solves). `gh_batch`, waiting through a solve, refused the first time it read it; in a live check it told the agent a dialog was open and not to retry. Now `gh_batch`, sweep and recompute report a dialog only once the reading has held for 2 s (`Core/DialogCheck`, unit-tested); a real dialog is still reported, about 2 s later. And a sweep sent while something is solving now waits for the solve (up to 15 s, as `gh_batch` does) instead of being refused at once, so the sweep after one that stopped on a slow definition no longer meets its own restore solve. Found by an independent review.
- **Remarks are no longer counted as warnings, and they come back with a script's results** - Grasshopper numbers its message levels Blank 0, Warning 10, Error 20 and Remark 255, so a remark ranks above an error by number. `outline`'s "level of warning or higher" counted a component with only remarks as a warning and showed the remark's text as one (a benchmark definition read "1 warning" that was a remark); next to a real warning, remarks were hidden everywhere; and `gh_script` `solve=true` returned only errors and warnings, so an agent asked to add a remark couldn't see it. Now `outline`'s summary and `problems`, `gh_inspect(action='tree')`'s note and the sweep's new-problem check compare by meaning (`Core/MessageLevels`, unit-tested); `solve=true`'s `messages` include remarks (`{"level": "remark", ...}`); and `outline`'s object lines show a component's remarks (`remark: ... (+1 more)`). `gh_script info` and `gh_inspect status` are unchanged.
- **A sweep on a slow definition answers before it re-solves the restored value** - The sweep's 45-second limit didn't count the solve that puts the control back. On a definition whose solve took about 34 s, a sweep stopped after one value as it should, then spent another 34 s restoring the slider, and the call (67.5 s) outlasted the AI app's limit of about a minute, so the agent got no answer (the slider was put back). Now, after a solve over 5 s, the control is set back and Grasshopper re-solves it after the answer; `restored` says so and for how long (`MIN AREA = 0.05 (Grasshopper re-solves it after this answer, about 34 s)`), and a call in the meantime gets the usual "busy" answer. Faster definitions restore before answering, as before.
- **Sweep and `watch` counts say how many items are empty** - A line such as `GEOMETRY 248 in 186 branches` counted empty (null) items as items. In a benchmark task (counting design geometry at five slider values), both Cordyceps's and Hyperceps's agents reported 248 pieces where 124 were empty slots, and Hyperceps's agent read the 248 from its sweep. The line now reads `GEOMETRY 248 (124 empty) in 186 branches`; with no empty items it is unchanged. It applies to `gh_document(action='sweep')` and `gh_batch`'s `options.watch`, which share the code. The skill says to report counts without the empty items.
- **An error during a long solve no longer waits for the solve to end** - Errors are also written to Rhino's command line, and `RhinoApp.WriteLine` from a background thread waits for Rhino's UI thread. While Grasshopper was solving, a tool's error answer, the new "busy" answer included, was held until the solve ended (found by the live check: a busy answer ready at 15 s arrived at 25 s). Log lines from background threads are now posted to the command line instead, and busy refusals are logged quietly, without a stack trace.
- **Images save to long paths** - `gh_document` `capture_viewport`, `capture_canvas` and `capture_region` failed with "A generic error occurred in GDI+" when the path was longer than 260 characters, as an AI app's scratch folders easily are (twice in one session). Images are now written through a .NET file stream (`Core/ImageFiles`), which handles long paths.
- **`options.timeoutSeconds` says what it limits** - The error for a value over 110 now adds that it limits checking and applying only, and the solve isn't counted; an agent asked for 180 s to cover a slow solve.

## Hyperceps [1.0.0] - 2026-10-14

First public release: github.com/yang-yibinn/hyperceps (release v1.0.0) and Rhino's Package Manager (`hyperceps`).

### Added

- **Plugin and skill are one product (version 1.0.0)** - Hyperceps is the Grasshopper plugin plus the Claude skill `hyperceps`, released together under one version number. The connection note now opens with `Hyperceps <version>:` and a short SKILL block: load the `hyperceps` skill if it isn't loaded, tell the user once how to install it if it's missing, and say so if the skill names a different version. The skill states the version it is for, and a unit test fails if the skill and the plugin project disagree (`Core/SkillPairing`). The README opens with "two parts, install both". Prompted by a test where an agent with the skill installed never loaded it.

- **`gh_canvas(action='outline')`: the canvas in one short call** - One line per top-level group, in data-flow order, with its colour, size, errors, child groups, what flows in (`in ←`) and what flows out with item counts and where it goes (`out: GRID LINES (28) → UPPER CURVES`); plus the sliders, toggles and value lists with their values, and the errors and warnings. A canvas without groups is described by its separate networks (inputs, named objects, ends) and its unconnected objects. `group='NAME'` (or a JSON list) shows how a group is wired inside: one line per object, upstream first, each with what feeds each input, port settings and what an unwired input holds; a child group is one line. `id='NAME'` with `depth=N` shows what feeds one object and what it feeds. Every name shown (a unique nickname, otherwise the shortest GUID prefix) works as an id in every tool. Replaces the opening `list` / `group_list` / `gh_wire list` / `info` calls: in a benchmark on a 340-component definition, reading the canvas took 4 turns and about 13k tokens, mostly GUIDs. gh_canvas gains one optional input, `depth`; nothing else changes. Host-free core in `Core/Outline`, unit-tested.
- **`gh_document(action='sweep')`: a slider at several values in one call** - Moves one number slider, value list or toggle through a list of values (or every value of a small control), solving at each, and returns one line per value: each watched output's item count and branches, a short preview of text, number and true/false outputs (so a checker script can be swept), the canvas's errors and warnings with any new ones named, and the solve time. The control is always put back and solved again, even if a solve fails. Every value and name is checked first; at most 20 values and 10 outputs per call, and it stops after about 45 s with what it has. Refused while the solver is off. In a benchmark run the agent had tested a slider by hand twice, about 6 turns plus restoring the slider in a later batch. gh_document gains three optional inputs, `id`, `values` and `watch`; nothing else changes. Host-free core in `Core/Sweep`, unit-tested.
- **Lichen Thalli in the outline** - When the canvas has [Lichen](https://github.com/yang-yibinn/Lichen) Thalli, the outline marks them `THALLUS`, shows the author's description (`authorDescription`) and properties (`authorProperties`), nests inner Thalli under outer ones, notes a T output wired to Lichen, and hides the Thallus's internal output component. Thalli are recognised by Lichen's fixed component ids and read through the field names Lichen saves, so Hyperceps doesn't depend on Lichen and works the same without it (`Core/LichenThallus`).
- **`gh_batch`: many canvas edits in one call** - One JSON spec of components, values, inserts, wires, disconnections, deletions, groups and port settings. Every entry is checked first and all errors come back at once, naming the entry and a likely fix; nothing changes unless everything is valid. The batch is then applied as one Grasshopper undo step (a single Ctrl+Z reverts it), with the solver paused, and solved once. Component names resolve by one strict rule (exact name, `Category/Name`, `Category/Subcategory/Name` or GUID; never a loose match), ports by index or exact name, and objects by ref, unique nickname, GUID or GUID prefix. Refs stay valid in later batches on the same document. A failure while applying is rolled back by undoing the batch's own record, so the file keeps its name and undo history. Results are compact (no wire echo, capped lists). Contract: `docs/gh-batch-schema.md`.
- **`gh_inspect(action='tree')`: data trees at a glance** - Branch paths and item counts of any output, read live from the canvas. Paths are grouped into runs (`{0;0}..{0;9}: 1 each`), with totals, path depth, items per branch, empty branches and nulls, plus short notes on the usual tree mistakes (mixed path depths, a grafted shape, indices Simplify would remove). Objects are named the gh_batch way — ref, unique nickname, GUID or GUID prefix, optionally `obj.port` — and a JSON list checks several outputs in one call. gh_inspect's arguments are unchanged; `id` simply accepts more for this action.
- **Agent guidance so agents batch without being told** - The connection note now opens with a seven-line working method (read once, one gh_batch per block, port settings instead of tree components, one-value-per-line panels instead of Text Split, nicknames and refs, tree checks, dry runs) and the naming conventions. gh_batch's description carries the core rules; gh_canvas and gh_wire point to gh_batch for two or more changes. After three single-step edits in a row, the result carries a one-line `nudge` toward gh_batch (`Core/SingleStepNudge`). gh_batch hints when a new Text Split could be a one-value-per-line panel, and a reused `#RRGGBB` group colour takes the matching existing group's transparency. The embedded guides (getting started, best practices, data trees) and two prompt templates now teach the batch workflow and the conventions, replacing "do not rename components while building". The skill document `skills/hyperceps/SKILL.md` holds the full method, conventions, data-tree mistakes and four worked examples.
- **Functional test script** - `tests/test_hyperceps.py` covers the spec's functional checks through the official MCP Python client, refuses to run unless the open document is the scratch file, and walks the person through the one-Ctrl+Z check. The `outline` check covers groups, nesting, a group's wiring, the view around one object and a canvas without groups; the `thallus` check runs on a separate hand-made file with Lichen Thalli, never clears it, and confirms every tool refuses to change a Thallus. The clearing checks refuse to run on a file that holds Thalli.
- **Tools can publish their own input schema** - `[McpInputSchema]` points a tool at an embedded JSON Schema that `tools/list` publishes instead of the generated one, so gh_batch's nested arguments are described to AI apps. Existing tools are unchanged.

### Fixed

- **gh_batch replaces an input's value instead of adding to it** - Setting a value on an input that already held a default (Series Start = 0, Trim Tree Depth = 1) left both: Start became `[0, 1]`, Depth `[1, 1]`. Found in a benchmark run, where it cost the agent several rounds of debugging. The input is now cleared first; one Ctrl+Z still restores the original values.
- **A ref can be reused when its object is deleted in the same batch** - Deleting `tb_trim` and creating a new `tb_trim` in one batch was refused as "already names an object"; deletes run first, so the name is now free.
- **Every bridge component on a canvas is protected** - Cordyceps hid (and protected from delete/clear) only the first Cordyceps component it found. With Cordyceps and Hyperceps installed side by side, the second one on a canvas was exposed, so `gh_document(action='clear')` could delete it. All of them, and what is wired to them, are now infrastructure.

### Changed

- **Release packaging** - `scripts/package.ps1` builds the plugin, runs the unit tests, checks that plugin and skill share one version, and writes the release files to `artifacts/`: the Yak package `hyperceps-<version>-rh8_0-any.yak` (plugin, license, README, icon and the skill in `skill/hyperceps`), `Hyperceps.gha` and `hyperceps-skill.zip` (entries `hyperceps/...`, readable by Claude's skill upload). It never publishes.
- **README rewritten for Hyperceps, with a design note** - The README now leads with what Hyperceps is, the two-part install, what it adds to Cordyceps, the benchmark (two like-for-like pairs) and the credits; `docs/design.md` describes the design and its decisions; `docs/gh-batch-schema.md` is the contract as built. The CI artifact is `Hyperceps.gha`.
- **Lichen Thalli are read-only to Hyperceps** - gh_batch refuses to `extend` a Thallus or to delete or group its hidden T output; gh_canvas refuses `group_add`, `group_remove`, `group_rename`, `group_color` and `group_delete` on a Thallus, and `delete` / `group_create` on its hidden output. Each error tells the user how to make the change with Lichen in Grasshopper. Before this, an agent could change a Thallus's membership as if it were a plain group, skipping Lichen's nesting and output-layout rules. Objects inside a Thallus can still be edited and deleted as usual.
- **Agent guidance reads the canvas with `outline`** - The connection note, gh_canvas's description, the getting-started guide, the optimize prompt, the common-errors guide and the skill document now start with `gh_canvas(action='outline')` instead of `list` / `group_list`, and say how to treat Lichen Thalli. The skill also tells agents in apps that load tools on demand to load `gh_canvas`, `gh_batch` and `gh_inspect` in one step (test runs spent a whole turn loading tools). Checking for errors after a change now also uses `outline`'s summary and problems list rather than `gh_inspect(action='status')`, which lists every component (about 37,000 characters on the test definition, and agents called it as a final check). After a benchmark run, the guidance also says to send the real batch rather than a dry run of the same block (a batch with errors changes nothing anyway; two benchmark runs both wrote their largest block twice), and not to read back a checker script with `gh_script get` before editing it (one run did so 7 times).
- **Every tool takes gh_batch's names for an object** - Wherever gh_canvas, gh_wire, gh_script and gh_inspect take an object id (`id`, `ids`, `sourceId`, `targetId`, `componentId`, move entries, group members), they now also accept an 8+ character GUID prefix, a ref from a gh_batch on the same document, or a unique nickname, by gh_batch's rules (`Tools/Batch/ObjectNames`). Group actions also take a group's name. A full GUID behaves exactly as before; argument names and outputs are unchanged. In a benchmark run, short ids from gh_batch results were refused by gh_script, gh_canvas and gh_wire four times, each costing a failed call and a look-up.
- **Hyperceps, a separate plugin that installs alongside Cordyceps** - Built from Cordyceps by Brooks Talley at commit bfef0e1 (v1.5.0 plus the parameter-spec fix below), developed under the working name Cordyceps+. New assembly (`Hyperceps.gha`), plugin, assembly and component GUIDs; the canvas component is *Params → Util → Hyperceps* (nickname `HYP`, icon with a "+" badge); default port 26930; MCP server name `hyperceps`; the skill is `skills/hyperceps`. Files saved with the Cordyceps+ component open with the Hyperceps component (same ids), so remove `CordycepsPlus.gha` before installing `Hyperceps.gha`. Rhino command-line log lines are prefixed `Hyperceps` and captures go to a `Hyperceps` temp folder, so the two plugins' output never mixes. Tool names, inputs and outputs are unchanged.

## Cordyceps [Unreleased] (as of bfef0e1)

### Fixed

- **An out-of-range parameter index no longer wires the wrong port** - `gh_wire(action='connect'/'disconnect'/'validate')` folded its range check into the same condition as the numeric parse, so an index past the end of a component's port list was indistinguishable from a spec that was never a number: it fell through to the name matchers and could connect to a parameter whose name merely *contains* that digit (`Plane 2` for `targetParam='2'`). The wire landed on a port nobody asked for and the call reported success. Grasshopper auto-numbers duplicated nicknames on exactly the variable-parameter components this hits, so digit-bearing names are ordinary there. A numeric spec now means an index and nothing else — an index outside the list is refused, naming the valid range, and no wire is created. That holds however the number is written: a spec too large for an `Int32` is refused as out of range rather than searched for as a name, which is the same defect at the far end of the range. The same rule (`Core/ParamSpecLookup`) now serves `gh_canvas(action='modifier')`, which already behaved this way, so both tools read a parameter spec identically.
- **`gh_wire` parameter errors say what was wrong** - A failed lookup previously reported only `"Source output not found: X"`; every wire-tool call site now returns the resolver's reason — the valid range for a bad index, the available names for a bad name — prefixed `Source:`/`Target:` so a bulk `connect` result says which end failed. The structured `availableOutputs`/`availableInputs` fields on `connect` failures are unchanged. One consequence: `disconnect` with an empty `sourceParam`/`targetParam` is now an error naming the missing argument, where it previously matched the first port (an empty string is a substring of every name) and disconnected a wire the caller never named.

## [1.5.0] - 2026-08-29

### Added

- **`gh_inspect(action='connection')`** - Answers "are you alive?" without touching the Rhino UI thread, so it still replies while Grasshopper is mid-solve or otherwise wedged. Reports whether the solver is running and since when, whether the UI thread is responsive, and the server's own state. Previously a busy solver and a dead bridge were indistinguishable — both produced silence until the client timed out, and the natural reaction (retry, or issue another `recompute`) actively made things worse.
- **Every tool response now carries a compact `status` block** - Each result reports Rhino, Grasshopper and Cordyceps health plus the document the call acted on, so an agent can see a busy solver or a wedged UI thread without asking. Purely additive; when a tool already returns a top-level `status` field its own data is preserved and the host block moves to `host_status`.
- **`GET /health` reports host state** - The health endpoint gains a `host` object carrying the same Rhino/Grasshopper/Cordyceps state as the `connection` action, so a non-MCP caller (a monitor, a shell script) can poll liveness over plain HTTP. Note that `activeDocument` is now the last document seen by the UI-thread heartbeat rather than a live read — the endpoint no longer touches the Grasshopper document from its HTTP worker thread, which is what lets it answer while the host is busy. It is null only while nothing is known yet.
- **`gh_canvas(action='modifier')`** - Read or set per-parameter data modifiers (`mapping='none'|'flatten'|'graft'`, `simplify`, `reverse`) — the right-click options on component ports. Omitted fields are left unchanged, and supplying only `id`/`side`/`param` returns the current state. These are idiomatic Grasshopper and central to data-tree design; previously the only ways to get a Flatten or a Graft were to insert explicit `Flatten Tree`/`Graft Tree` components or to ask a human to right-click the port.
- **`gh_document(action='snapshot_delete')`** - Delete a named snapshot to free memory or make room under the snapshot cap. A missing name is an error, never silent success.

### Changed

- **`gh_script(action='get')` reports the program that actually runs** - `source` is unchanged (the stored text), but whenever the running program can be read the response now carries `sourceDiverged` — true or false — plus `runningSource` when they differ, and `runningSourceUnavailable` with a reason when it cannot be read at all. Divergence is often legitimate — Rhino rewrites the `RunScript` signature of SDK-mode C# scripts as it builds them — so it is reported as a fact, not an error. Previously a clean `get` round-trip was read as proof that a write had taken effect, which it never was.
- **MCP `initialize` reports the informational version** - `serverInfo.version` was the four-field assembly version, so every 1.5.0 pre-release reported an identical `1.5.0.0` and a tester could not tell which build they were running. It now reports the full version string including the pre-release tag and build stamp (e.g. `1.5.0-rc.2+build20260827180257`), falling back to the assembly version when there is none.
- **The manual-install download is now the GitHub Release asset** - The README link pointed at `releases/Cordyceps.gha` committed on `main`. It now resolves to `/releases/latest/download/Cordyceps.gha`, which always serves the current release (and never a pre-release). The built `.gha` is no longer tracked in git: it is a build output, and `releases/` is gitignored.
- **`release.sh publish` builds the plugin it ships** - Publishing previously copied whatever `.gha` was sitting in the working tree into both the Yak package and the GitHub Release without building it, so the published binary's provenance rested on the file being tracked and the tree being clean. It now compiles from the release commit, which also lets a fresh clone of `main` publish.
- **CI uploads the built plugin** - `build-test` attaches `Cordyceps.gha` to every run - pushes to `develop`/`main` and every pull request - so a build of any commit can be picked up without a .NET toolchain. Artifacts expire and need a GitHub login; releases remain the distribution channel.
- **`gh_canvas(action='info')` reports data modifiers** - Every parameter now carries a `modifiers` object (`mapping`, `simplify`, `reverse`). Modifier state was previously invisible to the API, so an agent could not detect that a port was grafted — it had to be inferred from downstream branch counts, and round-tripping a document silently lost the information.
- **`gh_document(action='recompute')` is rejected while a solution is running** - Instead of expiring objects inside the running solution, it now returns a structured `{success:false, solving:true, solving_since}` result naming how long the solve has been going. Stacking recomputes into an in-progress solve is what raised the modal breakpoint dialog described below.
- **`gh_inspect(action='status')` no longer hangs during a solve** - This action needs the UI thread, so it previously blocked for the entire duration of a long solve (one measured case: ~32 minutes of silence from a read-only probe). It now returns a busy/blocked result promptly. Use the new `connection` action for a probe that never needs the UI thread at all.
- **`gh_script(action='set'/'configure')` falls back when a component has no `SetSource`** - The write path now mirrors the probe cascade the read path already used, falling back to a writable `Code` property. When a visible code input parameter blocks the write, or no writable member exists, the error names the cause and what was probed instead of surfacing an opaque host exception.
- **Guidance no longer encourages renaming components** - All agent-facing guidance (server instructions, action help, embedded guides, prompt templates) now recommends annotating with labeled groups (plus panels/scribbles) instead of nicknaming components while building — renamed components are hard to find on the canvas and it is not the Grasshopper convention. The `rename` action and `nickname` parameter remain fully functional for explicit use.
- **One Ctrl-Z now reverts a whole MCP action** - Every mutating `rhino_scene`/`rhino_render` action and `gh_canvas(action='bake')` runs inside a single named undo record (`Cordyceps <action>`). Previously each internal step was its own undo entry, so undoing a bulk operation (e.g. `set_layer` on fifty objects) reverted one object at a time.
- **The snapshot store is bounded (max 20 snapshots, oldest evicted)** - Snapshots are full document serializations that previously accumulated unbounded for the life of the Rhino session. Saving a new name beyond the cap now evicts the oldest snapshot and reports it in the response's `evicted` field; re-using a name replaces that snapshot in place. `snapshot`/`snapshots` responses now include `maxSnapshots`, and listed snapshots carry `createdAtUtc`.
- **Server teardown no longer stalls the Rhino UI** - Stopping the MCP server (deleting the component, changing its port, or closing the document) while a request was in flight previously froze Rhino for ~2 seconds waiting on handlers that could not finish until the UI thread was released. The port is still freed immediately; the wait for in-flight requests now happens in the background.
- **README install instructions** - Documented installation via the Rhino Package Manager (run `PackageManager`, search "Cordyceps", install) as the recommended method, with manual `.gha` download kept as the secondary option. Clarified that file-unblocking (Windows) / quarantine-clearing (macOS) is only needed for manual installs, and added the macOS `xattr` quarantine-clear command.

### Fixed

- **`gh_script(action='set'/'configure')` now recompiles the component** - Writing source stores text; it does not rebuild the program. Rhino compiles a script into a `Code` and keeps running *that*, so a component whose source was replaced went on executing its previous program — with `set` reporting success and `get` round-tripping the new text, because `get` was reading the stored source rather than the running program. Both write paths now ask the component to drop its cached build and rebuild (through Rhino's own `IScriptObject` hooks, which never expire or schedule a solution, so cluster editing is unaffected), then read the running program back and report it. `rebuilt` says whether the rebuild ran; when it didn't, `rebuildSkipped` (the component has no rebuild hooks and recompiles on its own) and `rebuildFailed` (a hook threw — the component is probably still running the old program) keep those opposite facts apart. `verified` says whether the running program matches what was written, with `sourceDiverged`/`runningSource` when it doesn't and `verificationSkipped` carrying the reason when the program could not be read at all — an absent answer never reads as a match. Compile errors still surface on the component rather than in the response — check `gh_inspect(action='status')` after writing code. One consequence worth knowing: the compile now happens inside the `set` call rather than at the next solve, so the first script write of a session can take noticeably longer.
- **MCP calls can no longer freeze the canvas with a "object expired during a solution" dialog** - Every tool call refreshed the Cordyceps component by expiring it immediately. When that landed while a solution was running, Grasshopper raised its modal breakpoint dialog ("The 'Cordyceps (MCP)' object expired during a solution"), which stops the canvas solving and makes every subsequent MCP call time out until a human clicks Close — fatal for unattended sessions. The refresh is now deferred to after the current solution, so the condition cannot arise from an MCP-initiated call. A burst of calls also coalesces into a single recompute instead of one per call.
- **Closing a Grasshopper document now stops the MCP server** - Previously the server only shut down when the component was deleted from the canvas; closing the `.gh` file left an orphaned server holding the port, so reopening the same file failed permanently with "port is already in use by another Cordyceps component" until Rhino restarted. The component now releases the server and port on document close/unload and restarts cleanly on reopen (including tab-switching between documents).
- **`gh_script(action='configure')` no longer wipes parameters on malformed JSON** - A syntax error in the `inputs`/`outputs` JSON was previously read as an empty list, which cleared every custom parameter and destroyed all wires while reporting `success:true`. Malformed JSON now returns `Invalid inputs/outputs JSON: ...` before anything is touched. A failed `code` update in a params+code call is also now machine-detectable (`codeSet:false` + `sourceError`, overall `success:false`) instead of being buried in a message string.
- **`gh_canvas(action='preview'/'enable')` report per-id results** - Unresolvable ids (and components that don't support preview/enable) were silently skipped with `success:true`; both actions now return per-id results like `delete`, with overall success false when any id fails.
- **`rhino_scene(action='layer_delete')` handles the current layer safely** - Deleting the current layer previously deleted/moved its objects first and then always failed (with a misleading error), leaving the document half-mutated; the destination layer could even be a child of the layer being deleted. The current layer is now reassigned and a valid non-descendant destination chosen *before* any mutation, and failures are diagnosed accurately.
- **`rhino_render(action='material_create')` actually applies PBR parameters** - `roughness`, `metallic`, `emission`, and `opacity` were set on a detached converted copy and never reached the document — every agent-created PBR material silently rendered as plain diffuse. They are now applied to the material that is added to the document; anything that can't be applied is reported in `notApplied` instead of silently dropped.
- **`rhino_scene(action='place_image', replace=true)` no longer destroys the old image on a failed add** - The previous picture was deleted before the new one was placed, so a failed placement (bad/corrupt image) lost the existing state; the new frame is now added first and old frames removed only on success. Attribute failures surface as a `warning` instead of being claimed.
- **Coordinates and slider values parse correctly on all locales** - Camera/light coordinate strings (`"10.5,0,3.2"`) and `gh_canvas(action='set')` slider values were parsed with the OS culture, corrupting values on comma-decimal locales (e.g. `10.5` → `105` on a German system). All numeric parsing is now culture-invariant.
- **Wrong-target operations now fail loudly instead of confirming** - `gh_wire(action='disconnect')` verified nothing and confirmed disconnecting wires that never existed (it now errors and lists the actual sources); `gh_canvas` group actions silently forked a new group on a typo'd `groupId`, swallowed malformed `ids` JSON, and let infrastructure-protection be bypassed via `group_rename`/`group_color`/`group_remove`/`group_add`; `gh_document(action='revert')` reported success with no canvas; `rhino_render(action='render', wait>0)` burned the full timeout then reported success on a non-Raytraced viewport; `rhino_render(action='sun')` ignored latitude/longitude/dateTime forever once manual azimuth/altitude had been used; garbage boolean strings silently mapped to true/false in `enable`/`preview`/`solver`; and `rhino_render` light actions accepted invalid input (bad location/target/color strings were silently skipped, `spotAngle` outside 0–90° passed through unchecked, and error messages named parameters that don't exist). All of these now return structured, actionable errors that validate before mutating.
- **Bulk operations report what they didn't do** - `rhino_scene` delete/hide/show/set_layer/set_name/set_color/select and `rhino_render` light_set/light_delete now return `notFound`/`notSelectable`/`failed` arrays and fail when nothing was affected, instead of `success:true` with a zero count. Bare `select` with no filter no longer silently selects the entire document (pass `type='all'` explicitly). Every `success:false` response now carries an `error` message (several view/material/env actions previously returned bare failures).
- **Nested layers work by full path** - Layer resolution now matches `Parent::Child` full paths, errors on ambiguous short names (listing candidates), and `set_layer`/`place_image` create nested hierarchies instead of failing on `::` in a layer name. `place_image` requires an absolute path (relative paths validated against the process CWD and broke later as linked textures).
- **MCP protocol robustness** - JSON-RPC response ids are echoed losslessly (large/fractional/string ids no longer destroy the response after the tool already executed, which caused clients to retry and double-apply mutations); argument binding/conversion failures return the standard `{success:false}` tool result instead of a raw `-32603` protocol error; whole-valued doubles like `300.0` are accepted for integer parameters; chunked request bodies are rejected instead of bypassing the size cap; `Accept: */*` is accepted; unfilled prompt-template placeholders render as an explicit `[argname]` marker instead of a bare word; ERROR-level log entries always reach the Rhino command line.
- **Deep data-flow hygiene** - `gh_document(action='clear')` inside a cluster editor no longer deletes the cluster's input/output hooks; bulk delete/enable/connect expire every affected component (not just the last), so cluster recomputes see all changes; `gh_inspect(action='trace')` no longer exposes Cordyceps infrastructure components and no longer NREs on phantom params; canvas/viewport capture no longer leaks bitmaps on save failure; component-registry caches no longer race or permanently cache a failed scan.

### Documentation

- **The silently-never-invoked `RunScript` trap is documented** - A script whose code only *defines* `RunScript` — with no top-level statements — compiles, syncs its output ports from the signature, and is then never called: outputs stay null with no error, warning or runtime message anywhere. On C# this is invisible to the divergence machinery (`verified:true` is correct — stored and running text are identical), so it is now called out in the common-errors guide and the script-setup prompt. Reported in #33, where it cost a reporter a full false-positive regression report.

- **Agent-facing docs corrected to match the real tool contract** - A documentation audit fixed several places where embedded guides, tool help metadata, and server instructions had drifted from the actual code:

  - Canvas-layout guide: the "Using Bounds" section now documents the real response shape (`bounds{x,y,width,height}` + `pivot{x,y}` from `action='bounds'`; list/find/info return pivot only) instead of nonexistent `right`/`bottom` fields.
  - Spacing guidance unified at **150px horizontal / 70px vertical** across all surfaces (canvas-layout and getting-started guides previously said 60-80px horizontal, contradicting the server instructions and tool help).
  - `gh_canvas(action='list')` help metadata now names the real `typeFilter` parameter (was `type`, which the tool does not accept).
  - `gh_document` undo/redo are now advertised as disabled (they are permanently-stubbed with a "use snapshots" error) in the tool help, server instructions, and README.
  - Prompt templates: `setup_script_component` no longer renders literal `{{...}}` malformed JSON (the renderer never unescaped doubled braces); `plan_definition`'s pattern step now reads the `gh://patterns/*` resources instead of misusing `gh_canvas(action='search')`; `debug_data_mismatch` names the real `gh_inspect(action='outputs')` fields (`branches`/`count`).
  - Component-not-found text now suggests `gh_canvas(action='search', query='...')` instead of the nonexistent `search_components` tool; rendering guide action lists now include `rhino_scene` `script` and `rhino_render` `env_delete`.
  - README: build command shows the required `-c Release` (Debug builds are blocked, and the csproj error message no longer claims `dotnet build` defaults to Release), the optional component input is correctly named **HttpPort**, and the tool count is stated accurately ("over 100 actions").

- **`gh_canvas(action='add')` now applies slider min/max/value/decimals** - Adding a Number Slider with `gh_canvas(action='add', type='slider', min=0, max=100, value=50, decimals=2)` previously ignored all four configuration params — the slider always landed at the default 0–1 range and 0.5 value, forcing a second `action='config'` call. It now reshapes parameters by name using the same LCS sync that `set` already used: parameters matching by name keep their connections, and wires on renamed/removed parameters are returned in a `lostConnections` array (with a `reconnectHint`), directly usable with `gh_wire(action='connect')` to restore them. `configure` is now also a **partial update** — omit a side (don't pass `inputs`/`outputs`) to leave it untouched, or pass `[]` to explicitly clear that side; previously, configuring only `inputs` would wipe all `outputs`. ## [1.4.11] - 2026-06-24

### Fixed

- **`gh_document(action='save')` can now overwrite an existing `.gh` file** - Saving over an already-existing `.gh` (binary) path previously failed every time with a bare `{"success": false, "error": "Failed to write file"}`, breaking incremental checkpoints, "save before mutating" safety nets, and any repeated save to the same path; only the first save (when the file did not yet exist) succeeded. The cause was a format-dependent overwrite flag — the `.gh` branch passed `overwrite=false` to GH_IO's `GH_Archive.WriteToFile`, while `.ghx` correctly passed `overwrite=true`. Both formats now save with `overwrite=true` (and `rememberPath=true`, matching Grasshopper's File→Save), so re-saving to the same path succeeds. Thanks to @anthonyesau for the detailed report (#14).
- **`gh_script(action='set'/'configure')` no longer silently leaves a Script component broken** - Setting a directive-less body on a bare unified **Script** component (which has no language until one is chosen) leaves it unable to compile — it fails at solve time with *"Can not determine input code language"* and emits no geometry. Previously `set`/`configure` returned `{"codeSet": true}` / a success message with no hint of the problem, so the natural retry (re-sending the same directive-less body) silently re-broke it. Both actions now return a `languageWarning` in that case, telling you to start your `code` with a directive (`#! python 3` / `// #! csharp`); doing so also recovers a component already in the broken state. The dedicated `C# Script` / `Python 3 Script` components are unaffected (they carry a concrete language and never need a directive). This narrows the remaining surface of the report by @anthonyesau (#15); the underlying language wipe is a Rhino-side behavior, but cordyceps no longer hides it.

### Added

- **Place raster images** - New `rhino_scene(action='place_image')` action places an image file into the scene as a real Rhino PictureFrame object at a caller-specified origin (`x`/`y`/`z`), size (`width`/`height`, model units), and optional in-plane `rotation` (degrees, flat on world-XY). Auto-creates the target `layer`, sets the object `name`, and returns the new object id. Optional `selfIllumination` (default true), `embedBitmap`, and `asMesh` flags control appearance and storage.

Supports UV tiling via `repeat` parameter and slot influence via `amount`. Omit `path` to remove a texture from a slot.
- **Material texture inspection** - `rhino_render(action='material_list')` now reports which PBR slots have textures assigned per material.

### Fixed

- **Server start failure now reports an actionable reason** - When the HTTP server can't bind its port (the port is held by another, non-Cordyceps application), the Cordyceps component previously showed a bare "NOT RUNNING" with no cause. It now surfaces the real reason on both the component's Status output and as a canvas error bubble — e.g. *"MCP server could not start on port 26929: … The port may be in use by another application — choose a different port (the HttpPort input) or close the process holding it."* (The existing "port owned by another Cordyceps component" message is unchanged.)
- **Clean server shutdown drains in-flight requests** - Stopping the server (removing the component, or changing its port) previously detached any request still being handled, and could null the shared document context out from under it — risking a crash in the worker thread. Shutdown now waits for outstanding request handlers to finish within a bounded budget before releasing shared state; a request that outlives the budget is detached safely and returns a structured *"server is shutting down"* result instead of faulting.
- **Concurrent commands are counted reliably** - The server's command counter and last-command label (shown on the Cordyceps component's Status output and in the `/health` response) were updated from concurrent HTTP worker threads without synchronization, so simultaneous requests could lose increments (an undercount) or read a stale last-command value. Counting now goes through a thread-safe helper (atomic increment + memory-barriered publish), so the count is exact and the last command is never torn. Snapshot storage (`gh_document` snapshot/revert/list) was likewise a plain dictionary written on the UI thread but listed off-thread; it is now a concurrent collection, so listing snapshots while one is being saved can no longer throw or read corrupt state. No change to any tool's behavior or output shape.
- **Server no longer hangs forever on a wedged operation** - Document access is serialized on Rhino's single UI thread; previously, if one operation never returned (e.g. an infinite-loop script component, or a modal dialog), the lock was held indefinitely and *every* subsequent MCP request blocked forever with no response, recoverable only by restarting Rhino. The lock acquire is now bounded: waiting requests fail fast with a structured `{"success": false, "error": "Document is busy…"}` result instead of hanging, so the server stays responsive. A re-entrancy guard also runs UI-thread-originated calls inline to avoid a self-deadlock. (RhinoCommon's `InvokeAndWait` cannot itself be cancelled, so a genuinely wedged operation still requires a Rhino restart to clear its holder — but it no longer takes the whole server down with it.)
- **MCP error contract honored at the server boundary** - Tool results carrying `{"success": false, ...}` are now reported to MCP clients with the transport `isError` flag set to `true` (previously hardcoded `false`, so failures looked like successes). Additionally, an exception thrown inside any tool method is now returned as a normal tool result (`isError: true`, body `{"success": false, "error": "<message>"}`) instead of escaping as a JSON-RPC `-32603` protocol error — making error reporting uniform across all seven tools. Genuine protocol errors (unknown tool, missing required parameter) still surface as JSON-RPC errors.
- **Script language preserved on `gh_script(set/configure)`** - Setting a script body without the Rhino 8 language directive (`#! python 3`, `// #! csharp`) no longer strips the component's language. Previously this caused "Can not determine input code language" at solve time and the component emitted no geometry — which bit anyone following the plain-body examples in the docs. The component's existing directive is now preserved automatically; a directive included in the new code is respected as-is.
- **`gh_inspect(action='docs')` flags failed introspection** - When a component's proxy can't be instantiated, the response now sets `paramsUnavailable: true` with an explanatory `note` instead of returning `success: true` with silently-empty `inputs`/`outputs`. Callers can now distinguish "component has no parameters" from "introspection failed" (the failure is also logged, retrievable via `gh_inspect(action='log')`). The field is absent when introspection succeeds, so the success-path response is unchanged.
